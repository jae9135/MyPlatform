# 세 번째 글 초안

**제목:** 입력 폼 오류 메시지, 사용자가 고칠 수 있게 만드는 방법  
**카테고리:** 웹 접근성·웹 품질  
**태그:** 웹 접근성, 웹 폼, 오류 메시지, 폼 검증, 웹 개발, QA  
**요약:** 필수 입력, 형식 안내, 오류 표시, 수정 방법까지 사용자가 이해하고 고칠 수 있는 웹 폼 점검 방법을 정리합니다.

---

회원가입이나 문의 양식을 작성하다가 제출 버튼을 눌렀는데, 화면이 그대로이고 무엇이 잘못됐는지 알 수 없었던 경험이 있나요? 오류가 입력란 아래에 작게 표시되거나 색깔만 바뀌면, 어떤 값을 고쳐야 하는지 찾기 어려울 수 있습니다.

접근성 있는 폼은 입력 전에는 무엇을 적어야 하는지 알려주고, 오류가 생기면 어느 항목이 문제인지와 어떻게 수정할 수 있는지를 설명합니다. W3C는 입력을 요구하는 경우 레이블이나 안내를 제공하고, 자동으로 발견한 오류는 해당 항목과 오류 내용을 텍스트로 알리도록 설명합니다. [W3C 폼 레이블 안내](https://www.w3.org/WAI/tutorials/forms/labels/), [오류 식별 기준 이해하기](https://www.w3.org/WAI/WCAG22/Understanding/error-identification/)

## 1. 입력란마다 분명한 이름을 붙입니다

입력란에 흐릿한 예시 문구만 넣어 두면 사용자가 입력을 시작한 뒤 항목의 의미를 잊기 쉽습니다. 입력란 가까이에 보이는 레이블을 두고, 레이블과 입력 요소가 연결되어 있는지 확인하세요.

```html
<label for="email">이메일 주소</label>
<input id="email" name="email" type="email" autocomplete="email">
```

`placeholder`는 입력 예시를 보여주는 보조 수단으로 쓰고, 항목 이름을 대신하게 두지 않는 편이 좋습니다. 예를 들어 “이메일 주소”를 레이블로 표시하고, 입력 예시는 별도 안내로 제공할 수 있습니다.

## 2. 필수 여부와 입력 형식을 미리 안내합니다

사용자가 제출한 다음에야 형식 오류를 알게 되면 수정과 재입력을 반복하게 됩니다. 입력 전에 필요한 정보를 짧게 설명하세요.

- 필수 입력인지 선택 입력인지
- 날짜나 전화번호를 어떤 형식으로 적는지
- 비밀번호에 필요한 조건은 무엇인지
- 입력 예시나 도움말을 어디에서 확인할 수 있는지

필수 항목을 별표 하나로만 표시한다면, 별표가 뜻하는 바도 폼 위쪽에 알려주세요. 화면에 표시된 안내와 브라우저가 읽을 수 있는 입력 정보가 서로 맞는지도 확인합니다. [W3C 폼 입력 안내](https://www.w3.org/WAI/tutorials/forms/instructions/)

## 3. 오류는 색상만으로 표시하지 않습니다

테두리를 빨간색으로 바꾸는 것만으로는 어떤 문제가 발생했는지 모든 사용자가 알기 어렵습니다. 오류가 난 항목 이름과 문제를 텍스트로 알려주세요.

예를 들어 다음처럼 구체적으로 작성할 수 있습니다.

- 모호함: “입력값이 잘못되었습니다.”
- 구체적 안내: “이메일 주소에 @와 도메인을 포함해 입력해 주세요.”
- 모호함: “필수 항목입니다.”
- 구체적 안내: “연락처를 입력해 주세요.”

오류를 텍스트로 표시하고, 색상이나 아이콘은 추가 단서로 함께 사용할 수 있습니다. W3C 기준의 핵심은 오류가 자동으로 감지되었을 때 어떤 항목의 오류인지와 무엇이 잘못됐는지를 텍스트로 알리는 것입니다. [W3C 오류 식별 기준](https://www.w3.org/WAI/WCAG22/Understanding/error-identification/)

## 4. 가능한 경우 고치는 방법도 알려줍니다

오류의 존재만 알리는 것보다 수정 방법을 함께 설명하면 사용자가 더 빠르게 해결할 수 있습니다.

```text
이메일 주소: 올바른 이메일 형식으로 입력해 주세요. 예: name@example.com
```

전화번호 형식, 날짜 범위, 비밀번호 조건처럼 시스템이 요구하는 규칙이 있다면 사용자가 미리 알 수 있게 안내하세요. 다만 보안상 공개하면 안 되는 정보까지 오류 안내에 노출하지 않도록 주의합니다. W3C는 수정 방법이 알려져 있고 보안이나 콘텐츠 목적을 해치지 않는 경우 오류 수정 제안을 제공하도록 설명합니다. [W3C 오류 수정 제안 기준](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)

## 5. 오류 메시지와 입력란을 연결합니다

오류 문구가 화면에 보여도 보조 기술이 어느 입력란의 설명인지 알지 못하면 사용자는 연결 관계를 놓칠 수 있습니다. HTML에서는 `aria-describedby`로 입력란과 도움말·오류 문구를 연결할 수 있습니다.

```html
<label for="email">이메일 주소 (필수)</label>
<p id="email-hint">예: name@example.com</p>
<input
  id="email"
  name="email"
  type="email"
  required
  aria-invalid="true"
  aria-describedby="email-hint email-error"
>
<p id="email-error">이메일 주소에 @와 도메인을 포함해 주세요.</p>
```

이 코드는 오류가 발생한 상태의 예시입니다. 오류가 없을 때는 오류 상태 표시와 오류 문구의 연결을 실제 상태에 맞게 갱신해야 합니다. 이름표시와 연결 방식은 웹 기술과 보조 기술 환경에 따라 확인이 필요하므로, 키보드와 스크린 리더로도 사용 흐름을 점검하세요.

## 6. 제출 후에는 오류 위치를 찾기 쉽게 합니다

폼에 오류가 여러 개 있다면 페이지 위쪽에 오류 요약을 보여주고, 각 오류에서 해당 입력란으로 이동할 수 있게 만들 수 있습니다. 오류가 하나라면 그 입력란 근처에 안내를 표시하는 방법이 적절할 수 있습니다.

제출 후 다음 항목을 직접 확인하세요.

1. 제출이 실패했다는 사실을 알 수 있는가?
2. 오류가 난 입력란 이름과 오류 내용이 텍스트로 표시되는가?
3. 키보드 사용자가 오류 위치를 쉽게 찾을 수 있는가?
4. 오류를 수정한 뒤 다시 제출할 수 있는가?
5. 서버에서도 같은 입력값 검증을 수행하는가?

브라우저의 기본 입력 검증은 빠르게 시작하기 좋지만, 기본 오류 안내가 구체적이지 않을 수 있습니다. 사용자에게 필요한 수정 방법과 오류 요약이 충분한지 실제 브라우저에서 확인하세요. 입력 검증은 접근성뿐 아니라 데이터 처리와도 관련되므로 서버 측 검증을 함께 적용해야 합니다. [W3C 입력 검증 안내](https://www.w3.org/WAI/tutorials/forms/validation/)

## 마무리 체크리스트

- 입력란마다 목적을 설명하는 보이는 레이블이 있는가?
- 필수 여부와 입력 형식을 제출 전에 알 수 있는가?
- 오류가 색상만이 아니라 텍스트로 전달되는가?
- 사용자가 무엇을 고치면 되는지 알 수 있는가?
- 오류 안내가 해당 입력란과 연결되어 있는가?
- 키보드와 스크린 리더로 오류를 확인하고 수정할 수 있는가?
- 클라이언트와 서버에서 입력값을 검증하는가?

오류 메시지는 개발자에게 문제를 알리는 로그가 아니라, 사용자가 작업을 마칠 수 있도록 돕는 안내입니다. 폼을 제출하기 전의 설명과 제출 후의 오류·수정 방법을 함께 점검하면 재입력 부담을 줄이고 더 많은 사용자가 서비스를 이용할 수 있습니다.
