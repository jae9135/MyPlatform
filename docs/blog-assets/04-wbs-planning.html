게시 제목 WBS를 만들기 전에 먼저 정할 5가지

카테고리 프로젝트 관리·업무 도구

태그 WBS, 간트차트, 프로젝트 일정, 프로젝트 관리, 일정관리, MyGantt

요약 작업을 나누기 전에 목표·범위·산출물·작업 크기·책임과 일정을 정리하는 순서를 소개합니다.

아래 본문을 복사해 티스토리 글쓰기 화면에 붙여넣으세요. 게시 제목과 카테고리, 태그는 티스토리 설정란에 각각 입력하면 됩니다.

프로젝트 일정표를 만들려고 엑셀이나 간트차트부터 열었는데, 작업 이름과 날짜를 어디서부터 적어야 할지 막막했던 적이 있나요? 이럴 때는 바로 날짜를 채우기보다 먼저 WBS를 정리하는 편이 좋습니다.

WBS(Work Breakdown Structure)는 프로젝트에서 해야 할 일을 관리 가능한 단위로 나누어 전체 범위를 계획하고 추적하는 구조입니다. NASA의 WBS 지침은 결과물 중심으로 범위를 나누고 일정·비용·기술 내용을 계획하고 관리하는 데 활용한다고 설명합니다. NASA WBS Handbook

실무에서 WBS를 시작하기 전에 아래 다섯 가지를 정리해 두면 일정표를 만들고 변경 사항을 관리하기 수월해집니다.

1. 프로젝트가 끝났을 때 무엇이 있어야 하는지 정합니다

먼저 프로젝트의 완료 상태를 한 문장으로 설명해 보세요. “시스템 개발”처럼 넓게 쓰기보다 누가 무엇을 사용할 수 있게 되는지, 어떤 결과물이 인계되어야 하는지 구체적으로 적습니다.

  • 고객이 실제로 사용할 수 있는 웹 서비스
  • 운영자가 참고할 사용자·관리자 안내서
  • 검수 결과와 배포 확인 자료

완료 조건이 모호하면 팀마다 서로 다른 결과를 상상하게 됩니다. 기능 목록뿐 아니라 문서, 테스트, 교육, 운영 인계 등 프로젝트 완료에 필요한 결과도 함께 확인하세요.

2. 범위에 포함되는 일과 제외되는 일을 구분합니다

요청받은 모든 일을 일정표에 넣기 전에 이번 프로젝트에서 수행할 일과 별도 협의가 필요한 일을 나눕니다. “한다”는 목록과 함께 “이번 범위에서 하지 않는다”는 항목도 기록하면 중간에 기대가 달라지는 일을 줄일 수 있습니다.

구분예시
포함로그인, 핵심 업무 화면, 통합 테스트, 배포 안내
제외 또는 별도 협의외부 시스템 연동, 기존 데이터 정제, 추가 모바일 앱

범위를 바꾸기로 했다면 변경된 결과물과 일정 영향도 함께 확인해야 합니다.

3. 결과물과 작업의 계층을 나눕니다

처음부터 세부 할 일만 늘어놓기보다 큰 결과물에서 시작해 하위 구성요소와 작업으로 내려가세요. WBS는 단계별 목차와 같기도 하지만, 각 항목이 프로젝트 범위의 어느 부분을 나타내는지 알아볼 수 있어야 합니다.

프로젝트
├─ 요구사항 결과물
│  ├─ 요구사항 목록
│  └─ 검토·승인 기록
├─ 서비스
│  ├─ 로그인·사용자 관리
│  └─ 핵심 업무 기능
├─ 테스트 결과물
│  ├─ 테스트 시나리오
│  └─ 결함 조치 결과
└─ 배포·운영 인계
   ├─ 배포 확인
   └─ 운영 안내서

조직이나 계약에 따라 산출물 중심, 기능 중심, 단계 중심 구조를 함께 사용할 수 있습니다. 중요한 것은 전체 범위가 빠지지 않고, 항목의 의미를 팀원들이 같은 방식으로 이해하는 것입니다.

4. 작업을 일정과 진행률을 관리할 크기로 나눕니다

“웹사이트 개발”처럼 큰 항목 하나만 있으면 기간과 진행률을 판단하기 어렵습니다. 반대로 “파일 열기”, “버튼 색 바꾸기”처럼 너무 작은 일만 나열하면 관리에 드는 시간이 커집니다.

작업 단위를 정할 때 아래 질문을 해보세요.

  • 담당자를 정할 수 있는가?
  • 완료 여부를 결과물이나 확인 기준으로 판단할 수 있는가?
  • 기간과 진행 상황을 주기적으로 확인할 수 있는가?
  • 이 작업이 끝나기 전에 시작할 수 없는 후속 작업이 있는가?

답하기 어려운 항목은 더 나눌 수 있고, 관리 단위로 삼기에는 지나치게 작은 항목은 묶어도 됩니다. 모든 프로젝트에 맞는 고정된 WBS 단계 수가 있는 것은 아니므로, 팀이 추정하고 추적할 수 있는 수준을 기준으로 조정하세요.

5. 책임자·일정·완료 기준을 연결합니다

작업 목록이 정리되면 각 항목에 담당자와 완료 기준을 붙이고, 선행 작업과 예상 기간을 확인합니다. 휴일과 승인 대기, 고객 검토처럼 실제 일정에 영향을 주는 시간도 빠뜨리지 마세요.

예를 들어 “통합 테스트”라면 담당자만 적지 말고 대상 범위, 테스트 완료 조건, 결함 수정 확인 방식까지 합의합니다. 이후 계획 시작일과 종료일, 실제 진행률을 기록하면 일정 변경이 생겼을 때 어디에 영향을 주는지 파악하기 쉽습니다.

WBS를 간트 일정으로 옮길 때

WBS는 범위를 구조화하고, 간트차트는 작업의 날짜와 순서를 시간축에 표시합니다. 두 가지를 함께 쓰면 계층별 작업과 선후 관계를 한 화면에서 검토할 수 있습니다.

MyGantt 같은 일정 도구에 옮길 때도 작업명만 입력하기보다 담당자, 계획·실제 날짜, 진행률, 산출물 정보를 함께 정리해 두면 일정표를 공유하고 보고할 때 유용합니다. 프로젝트를 브라우저에 저장하는 방식인지, 다른 사람과 공유할 수 있는 환경이 준비되어 있는지도 시작 전에 확인하세요.

작성 전 체크리스트

  • 프로젝트 종료 시 필요한 결과물과 완료 조건을 설명할 수 있는가?
  • 이번 범위에 포함되는 일과 제외되는 일을 구분했는가?
  • 큰 결과물부터 관리 가능한 작업까지 계층이 자연스러운가?
  • 각 작업의 담당자와 완료 여부를 판단할 기준이 있는가?
  • 선행 작업, 검토 시간, 휴일을 일정에 반영했는가?
  • 범위 변경 시 WBS와 일정도 함께 갱신할 방법이 있는가?

마무리

WBS는 작업 이름을 많이 적는 문서가 아니라 프로젝트 범위를 팀이 함께 이해하고 관리하기 위한 기준입니다. 목표와 범위를 확인하고, 결과물을 계층으로 나눈 다음, 담당자·완료 기준·일정을 연결해 보세요. 그 후 간트차트로 옮기면 일정과 진행 상황을 더 현실적으로 관리할 수 있습니다.
